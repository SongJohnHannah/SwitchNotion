# 本机附件 OCR

2026-10-28。按用户明确指定的 [SongJohnHannah/mediaocr](https://github.com/SongJohnHannah/mediaocr) 接入，固定到包含 Mac 原生支持的提交 [`0017d511`](https://github.com/SongJohnHannah/mediaocr/commit/0017d5119b53580c7b5277c00ed41d7f76733027)。Windows 与 Mac 都优先通过本机 stdio MCP 调用上游 `ocr_image` / `ocr_document`，不修改上游 Mac 实现。

配置 → 离线语音 →「检测并准备 mediaocr」可准备运行环境；也可执行 `npm run prepare:ocr`，Application Support 资料位置通过 `NOTION_SWITCH_ROOT` 或脚本首个绝对路径参数指定。按平台和架构创建独立 Python 环境、下载固定源码和引擎并核对代码散列；Mac 另执行上游已有引擎清单/合成样例验证。Windows 需要 64 位 Python 3.11；Mac 使用同架构的 Python 3.11+，可复用已发现语音 Python 创建独立环境，不修改其依赖。首次准备需要联网，识别在本机进行，不生成桌面分发包。

Mac 使用上游的 Mach-O 引擎、独立 worker 和通信适配；只在上游私有临时启动器上完成其要求的本地签名，不修改微信、Notion 或既有启动/音频配置。未准备时保留 Windows.Media.Ocr / Mac Vision 回退。明确要求全页强制栅格 OCR 时，若上游只返回文字层，则用系统栅格回退，返回实际引擎名称，不冒充 mediaocr 识别。

## 入口与行为

- 侧栏主动上传图片：明确要求 OCR/扫描/提取文字时使用本机 OCR，Flash 的普通画面理解及预览保留；其他文字模型先 OCR，将识别正文作为资料输入。原生上传路径、图片历史和原图存储保留。
- 主动上传 PDF：先提取文字层，缺少文字的页在本机补 OCR；问题明确要求 OCR/扫描文字时可对所有页识别。页码保留，不执行 PDF 动作或文档内指令。
- 页面附件：`read_notion_file` 支持图片及 PDF，下载后复核块版本；`ocr=true` 对 PDF 全部页识别。只有模型执行当前用户所需的读取时才下载，不遍历其他附件。
- 浮动 writer 的 PDF 沿用已适配的本地文档解析。原来的浮动图片处理入口保持，未用 OCR 文档上传替换其协议。

原始文件在本机处理，不提交给外部 OCR 服务。识别出的必要正文按用户既有授权进入配置的 DeepSeek；识别正文是资料，不是新的写入或外传授权。单文件仍限 16 MB，PDF 最多 200 页，系统回退每次进程最多八页；超过文字或队列限制明确失败。MCP 只取得应用复制的当前附件路径，模型不能借该接线指定其他本机文件。短期缓存最多八份，以源文件字节、引擎和页码散列匹配，准备 mediaocr 后不会沿用旧系统引擎缓存。退出先关闭 stdio，让上游执行其资源清理；超时只处理本次私有服务进程树。

Windows 的分词间隔只在相邻汉字间去除，不猜测或改正文字。OCR 可能有误字、漏字；返回标记与提示保留。图片 OCR 只读文字，不代表理解画面；动图按首帧识别。原文件不变，工作副本保存在随机私有目录并在任务结束后清理。

## 已有证据

真实 Windows mediaocr MCP 验收：中文合成图片返回 `合成识别，编号927`，无文字层 PDF 返回 `SYNTHETIC OCR CODE 927`，两份原文匹配，外部模型调用为零。此前 Windows 系统回退也已验证，存在部分误字，保留其限制说明。补查非 Flash 图片正文路由、续问归属、Flash 原图通道保留、Mac 命令/中文空格路径、分批、环境过滤、缓存及清理。

上游新增 Mac 源码散列核对通过，14 份原生引擎/模型资源共 87,376,600 字节与清单 SHA256 一致；Darwin arm64 的 Python/MCP 路径和结果解析通过契约调用。当前宿主为 Windows，未执行 Mac 原生引擎；仍需按 Mac 清单 N09 验收本项目内接线。复用既有测试，只更新已有路由 fixture 的依赖，没有新增永久测试脚本。
